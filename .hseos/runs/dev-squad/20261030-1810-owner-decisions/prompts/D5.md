## Por que existe
`docs/evolution/PLAN.md` exige, antes de qualquer código da W6, um ADR que fixe a abordagem de fork do Code OSS e o upstream. Está na seção "Pendências antes de abrir a W6". As premissas já decididas estão em:
- `PLAN.md`, linhas ~42-46 (invariantes) e linha W6 da tabela de ondas;
- `ADR-0043` (`.enterprise/.specs/decisions/ADR-0043-harness-evolution.md`);
- `ADR-0006` (AGENTS.md canônico, sem dependência de `~/.claude`).

Pontos-chave dessas premissas:
- **Kernel e IDE:** o kernel fica fora do Electron. A IDE Code OSS usa a API do kernel e uma extensão própria, com patches limitados no workbench.
- **Build:** upstream fixado e build descartável e reproduzível, gerando instalador independente.
- **Extensões:** o catálogo inicial só tem extensões licenciadas para redistribuição.
- **Electron:** não vira dependência do kernel.
- **Alterações externas:** são reconciliadas.
- **Plataformas:** Linux primeiro; macOS e Windows exigem certificação nativa (W7).
- **W6 entrega:** editor, terminal, Git, debug, planejamento, revisão, evidências e aprovações. Fechar ou atualizar a UI preserva o trabalho. Upstream e rollback são reproduzíveis.

## Entregas
1. Crie `.enterprise/.specs/decisions/ADR-0049-code-oss-fork-and-upstream.md` no formato do template, com `**Status:** Proposed`, data 2026-10-30, Context, Decision, Consequences, Affected Standards e Alternatives considered. O ADR deve decidir, com justificativa:
   1. **Base:**
      - fork do `microsoft/vscode` (Code OSS) em tag de release fixada, com patches mínimos no workbench e o grosso numa extensão própria;
      - VSCodium como base;
      - Eclipse Theia ou OpenVSCode Server;
      - só extensão sobre VS Code/Code OSS de terceiros, que não cumpre "instalador independente".

      Recomende uma e explique por que as outras não servem.
   2. **Política de upstream:**
      - pin por tag e SHA;
      - cadência de rebase;
      - critério de atualização de segurança;
      - patches mantidos como série versionada e aplicáveis em CI, com teto de patches no workbench.
   3. **Build reproduzível e descartável:** toolchain fixada e verificação de hash do artefato. O ambiente separado dela é a "toolchain da IDE separada" citada no PLAN.
   4. **Marketplace e licenças:** Open VSX, sem o marketplace da Microsoft (termos de uso). Catálogo inicial só com extensões redistribuíveis. Remoção da telemetria e da marca da Microsoft (product.json).
   5. **Fronteira com o kernel:** a IDE fala com o kernel só pela API versionada local e autenticada, com a mesma autoridade de CLI/API/SDK. Nada de SQLite compartilhado. O Electron não entra no kernel.
   6. **Onde fica o código:**
      - repositório separado, ou
      - pasta excluída do pacote npm (`files` do package.json).

      O G3 não comporta o código no pacote. Escolha e justifique.
   7. **Rollback e preservação do trabalho** ao fechar ou atualizar a UI.
   8. **Plataformas:** Linux primeiro. macOS e Windows só com execução nativa certificada (W7).
   9. **Riscos e mitigação.**

   Onde houver incerteza factual (por exemplo, a versão atual do Code OSS ou os termos exatos do marketplace), não invente número. Escreva "a confirmar no aceite" e liste como pergunta aberta numa seção "Questões para o aceite".
