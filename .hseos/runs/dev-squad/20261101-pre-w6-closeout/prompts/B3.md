## Contexto
- **Requisito F14-R1** (`docs/evolution/requirements.json`, ~:334-353): contexto e memória mantêm fonte e autoridade.
- **Gap aberto:** consumidor real para memória ampliada.
- **Caminho no código:**
  - `tools/cli/lib/memory-context-source.js`, usado em `engineering-task-extensions.js` (~:591, 814, 961);
  - `MEMORY_DATA` em `packages/agent-context/context-assembler.js` (~:229).
- **O que já existe:** o MRTR com consumidor real (Claude Code) provou `memory.write` e `memory.delete` via MCP (`.hseos/runs/dev-squad/20261030-1810-owner-decisions/logs/MRTR-CLAUDE.md`). Ainda falta provar que a memória recuperada **entra no contexto** de uma tarefa.

## Entregas
1. Uma tarefa de engenharia com fonte de memória configurada registra no ledger, ou no recibo da sessão, quais memórias entraram no contexto montado. Para cada uma: `memory_id`, `origin`, `trust`, `authority` e o digest do conteúdo.
   - Memória `untrusted` não entra sem `include_untrusted`, conforme o assembler.
   - Se esse registro já existe, prove com teste. Se não existe, acrescente-o a partir dos dados que o assembler já tem.
2. **Teste de jornada**, com provider determinístico e banco ativado em fixture:
   - grava a memória pelo caminho MCP (`memory.write`);
   - roda a tarefa com fonte de memória;
   - confere no ledger que a memória entrou no contexto, com proveniência e autoridade `data`.
   - **Negativos:** memória de outro projeto não entra; memória `untrusted` sem opt-in não entra.
3. **Runbook:** seção F14 de `docs/evolution/runbooks/f14-f15-real-consumers.md`. Quem cria esse arquivo é a B2; se ela ainda não o tiver criado no seu worktree, crie você só a seção F14. O Commander resolve o merge. A seção descreve:
   - como rodar com cliente real: Claude Code via MCP mais tarefa de engenharia, ou Codex;
   - o recibo exigido;
   - o teto.
